Run a Todo app in Kotlin

This follows the same flow as JavaScript: open a database, read and watch tasks, add one with a command, then sync it. Every snippet comes from one Kotlin file for the Android binding in bindings/android, which is not published.

Verification boundary: the documentation build compiles this file with the binding, using the installed Kotlin compiler with warnings as errors, and runs it on an Android emulator (x86_64, API 37, 16 KiB pages) against the real native core: python3 docs/public/run_kotlin.py build, then python3 docs/public/run_kotlin.py run. It runs as a plain program through app_process, not as an installed app, so it is not an APK, Gradle or device certification. The certified Android artifact predates parts of this API; build the binding from source. See platforms.

Differences from JavaScript: database calls are suspend functions, so call them from a coroutine. Values are typed: row fields are Cell values such as Cell.StringValue("Buy milk"), and command arguments and results are JSONValue. A Query is a value with predicates and an order, and sync is explicit, step by step.

1. Describe your data

A schema lists your tables and the type of each column. Here a task has a title and a done flag. The imports serve the rest of the file: dev.hoyadb is the binding and dev.hoyadb.testing provides the stand-in server used in step 7.

{{example:kotlin:schema}}

A column is required unless you pass optional = true. Other kinds are ColumnKind.Integer, Float, Timestamp and Reference.

2. Open one database

The following steps are the body of todoGuide(ui), a suspending function in the example file. Its ui parameter is the Executor that runs your observation callbacks. Create the database with it and open it with the schema, here in memory.

{{example:kotlin:open}}

On Android, pass an executor that posts to the main looper. The example's main passes a single background thread, because it runs without an app. Open once and share the database. Memory storage is lost on close. For data that persists, openProtected takes an Android Context, a name and a 32-byte key that your app owns; see persistence and key ownership.

3. Query

A Query names a table, its predicates and an order. Keep it in a value: the next step watches the same query. Fetching runs locally, so it works offline.

{{example:kotlin:query}}

A new database has no tasks yet, so this first fetch is empty. Operators are Eq, Ne, Lt, Le, Gt, Ge and In. Several predicates must all match.

4. Watch the results

observe calls your lambda with the query's current rows, then again after each change. Here it hands the rows to Seen, a small thread-safe recorder defined in the example file that lets it check what the callback received; in an app, update your screen state instead.

{{example:kotlin:observe}}

The callback receives an ObservedValue: Rows, or Failure with an error kind. Close the returned Subscription when the screen goes away.

5. Define a command and its local handler

A command has a definition, a stable name with a version suffix and the arguments it takes, and a local handler that runs on the device. Your server recognizes the command by its name. The handler reads its arguments from its scope and inserts the new task through it.

{{example:kotlin:command-definition}}

Use the scope, not the database, for reads and writes inside a handler: they commit together when the handler returns. The as casts keep the example short; validate the shape of arguments and results in an app.

6. Run it

command runs the handler from step 5 with the arguments and a captured context, and returns the key of the queued command with the handler's result.

{{example:kotlin:execute}}

The new task already appears in the watched query from step 4, under a temporary local: ID, and the command waits in the queue to sync. The example fixes the time at 1000 ms so that it is repeatable; pass the current time in an app. The context is recorded with the command. It is information for your server, not proof of who the user is.

7. Your server

Your server has its own handler for add-task-v1, and it decides the final outcome. Here FakeTransport from dev.hoyadb.testing plays the server and answers with the task's real ID.

{{example:kotlin:backend}}

In an app, replace it with your own HTTP client that sends the envelopes from the next step to your API.

8. Sync and confirm

preparePush returns the waiting commands as JSON envelopes; send them to your server and pass its answer to receiveWire. Each confirmed answer waits in pendingReconciliations() until you reconcile it. A command that created rows must map every local: ID it created to the ID your server assigned.

{{example:kotlin:sync}}

After reconciling, the command is applied and the task has the ID server-task-1. See reconciliation.

9. Close

Close the subscription when the screen no longer needs it.

{{example:kotlin:close}}

Close the database itself when your app shuts down, as the finally block in the source file does. Continue with the Kotlin reference. The verification result records the build and the run.

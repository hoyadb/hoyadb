The host loop

  1. Sample UTC milliseconds and bounded jitter, then call prepare_push / preparePush.
  2. If envelopes are nonempty, send their canonical frozen bodies through your transport. Do not reserialize business numbers through JavaScript Number.
  3. Record receipts with receive or the SDK wire codec, preserving command/entity correlation.
  4. For pending authoritative outcomes, supply an application reconciliation plan.
  5. Schedule the returned next due time. Stop host scheduling on close/reset.

The commands example proves that a retry has the same envelope bytes. Core persists attempts and deadlines. Transport failure does not invent an applied or rejected outcome; the queued action remains eligible according to core deadlines. The library does not supply your TLS, authentication, backend implementation or request timeout policy.

Receipt is not local application

A receipt without an outcome acknowledges delivery and stops ordinary retransmission. An authoritative outcome is retained until its local reconciliation succeeds. pending_reconciliations exposes this recovery work; request_redelivery explicitly re-arms a lost outcome path. Repeating an identical receipt is idempotent; a conflicting second outcome is Protocol.

Defaults and reopen

The current SyncOptions defaults are capacity 1000, history 100, initial delay 1000 ms, multiplier 2 and maximum delay 60000 ms. Reopening an existing ledger with incompatible options fails. Capacity and history are distinct: retained non-live history is bounded separately from active queue work. See recovery before deleting anything.

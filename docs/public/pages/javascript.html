JavaScript guide

This guide explains the JavaScript application API used in getting started: how to import it, describe and open a database, read and watch data, write commands, and sync. Every snippet comes from one tested Todo app. The packages are local, unpublished 0.1.0 builds.

The following sections revisit parts of that file by topic, not in execution order. The getting started page follows it step by step.

Schemas and value types

Import the application API and describe each table with defineSchema, table and column. This is the schema of the Todo app.

{{example:application:schema}}

Each column has a type. You read and write ordinary JavaScript values; the column type decides how they are stored:

ColumnJavaScript value
column.string()string
column.boolean()true or false
column.integer()number. Values beyond Number.MAX_SAFE_INTEGER are rejected. Use column.integer({bigint: true}) to always read and write bigint.
column.float()finite number (negative zero is rejected)
column.timestamp()a Date on read; a Date or milliseconds on write. Use column.timestamp({bigint: true}) for bigint milliseconds.
column.reference()the ID string of another row

Columns are required unless you pass {optional: true}. An optional field can be null or simply missing; the two stay different. Relations connect tables: relation.toOne(table, {foreignKey}), relation.hasMany(table, {foreignKey}) and relation.manyToMany(table, {through, sourceRelation, targetRelation}). A to-one relation's foreign key holds the related row's ID.

Opening a database

openDatabase takes the schema and everything the database needs from your app. This call opens the Todo app in memory, with its server transport and confirmation callback, then pulls the server's tasks once.

{{example:application:open}}

Open one database per store when your app starts, share it, and close it on shutdown. Options:

  • schema: the result of defineSchema.
  • engine: 'memory': in-memory storage, lost on close. This is the default.
  • context: a function returning plain JSON about the current user. It is recorded with every command. It is information for your server, not proof of authorization.
  • clock: a function returning the current time (a Date, milliseconds or bigint). It defaults to Date.now.
  • entities: {scope, tables}: tables that sync field by field with your server (see entity tables).
  • transport and reconcile: your server connection and confirmation callback (see sync). They are only used when you call sync() or startSync().

To keep data in the browser, pass filename and a 32-byte encryptionKey (a Uint8Array your app owns and stores securely). Storage is always encrypted; there is no unencrypted option. It needs a dedicated worker and the browser's private file system (OPFS). Node currently supports memory storage only.

Queries

This query reads the open tasks, sorted by title. It runs locally and returns plain rows.

{{example:application:query}}

db.query(table) builds a query. where(field, operator, value) accepts =, !=, <, <=, >, >= and in; several where calls must all match. orderBy(field, 'asc' | 'desc') and limit(n) shape the result, and fetch() returns plain rows. A field can follow a to-one relation, such as 'author.name'. db.related(table, id, relation) builds a query for related rows.

For single rows, db.table(table) offers insert(fields), which returns the new row, and findById(id), which returns a handle with fetch(), a partial update(fields) and remove().

Watching data

A query can also be watched. The callback here keeps the titles of the open tasks up to date.

{{example:application:observe}}

observe(callback) returns a stop function at once. Its ready promise settles when the watcher is registered, and rejects with the error if registration fails. The callback receives plain rows: first the current result on a later turn, then again after each change. Pass a second callback to be told about delivery errors. observeCount(callback) watches only the number of matching rows. Calling the stop function more than once is harmless, and closing the database stops every watcher.

Commands: three pieces

A command has three parts, and it helps to keep them apart:

  1. The definition: a stable name with a version suffix, and the arguments it takes. The name is how your server recognizes the command.
  2. The local handler: runs on the device the moment you call execute, so the UI updates immediately.
  3. The server handler: your backend's own code for the same command name. It decides the final outcome. HoyaDB never runs your server code.
{{example:application:command-definition}}

Argument types are 'string', 'reference', 'integer', 'float', 'boolean', 'array', 'object' and 'any', or {type, optional: true}. Use 'reference' for an argument that holds a row ID, so the command waits until that row's ID is confirmed by the server.

The handler's db is not your app's database object. It is a view limited to this command: query, table and related. Its reads see the handler's own earlier writes, and all of its writes are committed together when the handler returns. If the handler throws, nothing is kept. A handler cannot run another command, and while it runs, writes through the app's database fail with Busy. ctx.identity is read-only, and ctx.now() returns the command's time.

{{example:application:execute}}

db.command(definition) binds a definition to one database. execute(args) resolves to the handler's result. executeWithReceipt(args) also returns the command's key, which you can pass to db.observeOutcome(key, callback) to hear the server's final answer.

Sync and the server

HoyaDB never makes network requests itself; you supply a transport. In the Todo app, the test backend from @hoyadb/testing plays the server: it holds two tasks and has a server handler for each command.

{{example:application:backend}}

Your transport's push(envelopes) receives the waiting commands and edits as plain objects. A command envelope has its command name, args, context and an idempotencyKey. Push returns one answer per envelope, carrying the same key with status: 'applied' or 'corrected' and a result, or status: 'rejected' and a reason. pull(since, scope) returns the server's changes after a checkpoint. A real transport sends these to your HTTP API. Large integers arrive as bigint, so serialize them with care.

{{example:application:sync}}

sync() sends waiting work, records the answers, confirms them through your reconcile callback, then pulls when entity tables are configured. startSync() does the same in the background: it retries with backoff and pulls every 30 seconds by default (pullIntervalMs). stopSync() stops it.

reconcile(pending) is called for each answer the server confirmed, and returns a plan. The pending object has:

  • key: the command's key.
  • kind: 'command' or 'entity'.
  • outcome: the server's answer, with its result as plain values.
  • created: the IDs this write created locally, each mapped to its table.

created is read from the database's stored records, so it is still correct after a restart. The plan needs mappings from each created local ID to the ID your server assigned, plus optional authoritative writes. A command that creates no rows, like complete-task-v1, returns empty mappings. Your code decides the mapping for commands, because only your server's result says which ID belongs to which row. Rows created in entity tables keep their IDs, and HoyaDB adds those identity mappings for you without overriding yours. See commands that create rows and reconciliation. For a rejected command, return empty mappings, then call db.rollback(key) if you want to undo its local changes.

Commands that create rows

A handler can insert rows as well as update them. add-task-v1 creates one task.

Rows a command creates get temporary IDs that start with local:, and the UI can use them at once. Another command can refer to such a row through a 'reference' argument; it then waits to sync until the row's real ID is known.

The server answers add-task-v1 with the new task's ID. The reconcile callback in the open options maps the one created local ID to that ID, and HoyaDB renames the row in the table, in references and in watched queries.

Entity tables

The Todo app lists todos in its entities option, so edits made outside a command sync by themselves. This update renames a task.

{{example:application:entity}}

Tables listed in entities sync field by field. An update outside a command records only the changed fields, and the newest value of each field wins when your server's changes are pulled. Other tables change only locally, unless a command writes them. See entity sync.

{{example:application:entity-insert}}

A row inserted into an entity table outside a command gets its final ID immediately (it starts with entity:), so no mapping from you is needed.

Advanced: the host API

@hoyadb/client/host is the lower-level API that the application API is built on. It uses tagged values (j.string('x')), explicit runtimes, and manual preparePush and receiveWire steps. Use it when you need exact control of the wire format. The excerpts below come from a separate tested tour, which runs it directly against the WebAssembly core and also covers CRUD, relation queries, observation, entity patches, errors and reopening.

First load the WebAssembly core once and wrap it in a runtime. Every host database opened later uses this runtime.

On the host API, every operation on a command is explicit:

  • reconcile and reconcileGuarded confirm a command.
  • rollback undoes a processed rejection.
  • cancel withdraws queued, sent or rejected work.
  • forget removes finished history.

Frames are limited to 1 MiB, 64 nesting levels and 100 000 nodes. Methods are described in the SDK reference.

A configurable stop-or-discard conflict policy (ConflictPolicy, a discard operation, an onResolution callback and a discarded state) is specified in SPEC-0040 but not implemented. Today a conflicting rollback or correction returns RollbackConflict and changes nothing. Cancel is different: on an inverse conflict it can record Cancelled while retaining recovery data.

For named business handlers and commands that perform several writes, follow the Rust Todo command walkthrough: create a task, then complete it and add an activity entry atomically. It separates argument declarations, invocation values, handler code and the returned receipt.

Run the complete Todo flow

From the checkout, run cargo run --manifest-path examples/Cargo.toml --bin rust_todo --offline --locked. This example uses the real memory adapter and CommandDatabase, which owns local data, observations and durable command work. The local crates are unpublished.

The examples import a small support module for types, field construction and a ready-future runner. That runner works with this memory adapter; use ordinary .await on your application's executor for adapters that suspend.

1. Define the schema

The Todo table has a required title and done flag. column is an example helper that creates a required column.

{{example:rust_todo:schema}}

2. Open one owner

Share the owner according to your host's task model. The namespace identifies this store's queued commands; use a unique value for a new store and retain it across reopens. Memory storage disappears on drop. Use protected SQLite for durable storage and manage keys in the application.

{{example:rust_todo:open}}

3. Observe

Rust supplies notifications for the host to deliver. Register a query, then drain notifications on the host clock. This is explicit, unlike a binding that schedules callbacks for you.

{{example:rust_todo:observe}}

4. Define and run a local command

The definition names the backend action and its argument types. After admission through begin, run the local handler through scope_* operations. finish atomically commits the optimistic row and durable queue record. If a real handler fails, call abort rather than leaving an active request. App-supplied context is not server authentication.

{{example:rust_todo:definition}}

Capture a request and its arguments. If admission returns false, retain and retry the request before using the scope; this isolated fixture is admitted immediately.

{{example:rust_todo:begin}}

Run the local writes through that request, then finish. The complete example checks that the new task has a local ID and one command is pending.

{{example:rust_todo:handler}}

5. Query the committed data

The row is immediately available offline, with a temporary local: ID. The registered observer receives the committed change.

{{example:rust_todo:query}}

6. Supply a server transport and reconcile

The stand-in below marks the command applied. A production host sends the core's prepared envelope to a server that authenticates, deduplicates and runs its own handler, then feeds its reply back through the wire codec. Rust does not install a network client or a background scheduler for you.

{{example:rust_todo:prepare}}

The prepared batch contains the queued envelope. In this test the backend reply is represented directly by an Applied outcome.

{{example:rust_todo:backend}}

The application maps every command-created ID to its authoritative ID. Reconciliation then renames the row and its references atomically. See recovery for corrections and conflicts.

{{example:rust_todo:sync}}

7. Dispose and close

Release the observer when it is no longer needed, then close the owner.

{{example:rust_todo:cleanup}}

Protected does not mean authorized

Encryption protects local storage at rest with externally supplied keys. The application still owns authentication, authorization, TLS, backend policy and secure key retention. Context identity is application-provided data; it is not proof of authorization. Never log keys or whole wire frames that may contain business data.

Fail closed

Missing or wrong keys, unsupported engines and incompatible stores refuse protected open. There is no password derivation, rotation, arbitrary-store import or automatic format migration API promised here. DiagnosticSnapshot is a restricted count/Boolean view, while explicit fetch APIs intentionally return application data. Debug output is redacted in sensitive types; it does not make arbitrary application logs safe.

Host boundary limits

ABI1 frames are limited to 1,048,576 UTF-8 bytes, 64 containers and 100000 nodes. Tags and envelopes consume the same budget. Read-only fetch returns a complete snapshot or LimitExceeded; push/drain may return bounded owned prefixes. Code must handle errors rather than truncate values itself.

Use a separate binary key channel for protected facade open. A C collector must copy its borrowed reply before returning. Native pointer accessibility remains the caller's responsibility; panic containment does not make invalid foreign addresses safe.

Backups and deployment

Backup policy is platform-specific. Browser reports unsupported; memory reports not_applicable. Native wrappers apply their documented platform policy. Encryption, backup exclusion, and a source build each establish different facts; none alone proves a release is supported. Read platform limits.

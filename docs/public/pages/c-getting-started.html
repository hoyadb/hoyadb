Run a Todo app over the C ABI

This follows the same flow as JavaScript: open a database, read and watch tasks, add one with a command, then sync it. Every snippet comes from one C program that the documentation build compiles with warnings as errors and runs.

The C interface is not a database API with functions per operation. It is a framed JSON ABI declared in hoyadb.h: you send one JSON frame, such as {"abi":"1","op":"fetch","owner":"…","args":{…}}, and receive one JSON reply, {"abi":"1","ok":true,"value":…} or {"abi":"1","ok":false,"error":{"kind":…}}. The Swift, Kotlin and React Native bindings are built on these same frames. Use it to write a binding for another language, or when you need exact control. The native reference gives the C signatures and ownership rules; the platform contract defines the operation frames.

Build the static library with cargo build --manifest-path crates/hoyadb-native/Cargo.toml --release --offline --locked, then link libhoyadb_native.a with the Security and CoreFoundation frameworks on Apple platforms. python3 docs/public/run_native.py build and python3 docs/public/run_native.py c reproduce the documentation build.

1. Replies are borrowed

Every call takes a collector function and a context pointer. The collector below copies the reply into memory the application owns, and call sends one frame and returns that copy. Two small helpers are defined at the top of the full file: CHECK prints a message and exits when a condition fails, and ok tests whether a reply starts with "ok":true.

{{example:c:reply}}

Status 0 means the library called the collector exactly once with one complete reply, and those bytes are valid only during that call. Copy them before the collector returns. The library never returns memory for you to free: the copy is yours, so you free it. Status 1 (an invalid call) or 2 (a contained internal failure) means there is no complete reply to read. Status 0 still needs a check of "ok", because a rejected operation is an ordinary reply; this example's call stops on any reply that is not ok. In an app, report the error kind instead of exiting.

The example keeps its JSON handling short. It builds frames with snprintf into one 4 KiB frame buffer, from values the library returned, and its string_after helper copies the string that follows a marker in a reply. That only works for these known fixtures. A real application should use a JSON library.

2. Open

First confirm that the library speaks ABI 1. Then one open frame carries the whole configuration: engine, schema, migrations, namespace and options. Counts and times are decimal strings. Memory storage takes no key.

{{example:c:open}}

The reply's value is an owner handle that every later frame names. A key never goes into JSON: a protected store takes its 32 key bytes as a separate argument. See persistence and key ownership.

3. Query

A fetch frame carries the same query shape as the other bindings: a table, predicates, an order, a limit and a source. Values are tagged with their kind.

{{example:c:query}}

A new database has no tasks, so the value is an empty array. Rows come back as objects with an id and fields.

4. Observe

There are no callbacks into your code. observe returns a subscription handle, and drain returns the events that are ready, when you choose to ask.

{{example:c:observe}}

The first event for a subscription is its current result, here no rows. Drain again after writes, for example once per frame of your UI loop.

5. Start a command

A command is several frames: a request ticket, begin, the handler's scoped writes, then finish. Your C code between begin and finish is the local handler. It starts with a ticket.

{{example:c:command}}

Keep the ticket: every frame of this command names it.

6. Run the local handler

begin carries the definition, the arguments and the captured context; its value is true once the command is admitted. scope_insert writes through the command, and finish commits its writes together and returns the command's key. Rows a command creates use proposed IDs that start with local:.

{{example:c:execute}}

The next drain shows the task to the subscription from step 4. The example fixes the time at 1000 ms so that it is repeatable; pass the current time in an app. The context is information for your server, not proof of who the user is.

7. Sync and confirm

prepare_push returns the waiting commands as envelopes. Your server runs its own handler for add-task-v1 and answers each envelope; pass that answer body to receive_wire. Then reconcile the command, mapping every local: ID it created to the ID your server assigned.

{{example:c:sync}}

Afterwards the task is stored as server-task-1 and the local ID no longer exists. See reconciliation.

8. Close

Unsubscribe, close the owner, then free the strings you copied.

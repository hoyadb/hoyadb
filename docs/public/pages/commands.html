Two commands for a Todo app

A command is a named action that works offline. Its local handler changes the database now; your server processes the action later. We will create a task, then complete it and record an activity entry.

CommandArgumentLocal business logicHandler's JSON result
create-task-v1title: StringTrim the title, reject a blank title, insert an unfinished tasktask_id
complete-task-v1task_id: StringSet done to true and insert an activity entrytask_id and activity_id

Every snippet comes from one runnable Todo program. We start with its caller code, then unpack the helper definitions; this page revisits those definitions by topic rather than file order. The full program puts the definitions before the calls.

Start with the calls your application makes

The example opens db with open_todo_app(). Call the application's create_task function with a title. It returns a CommandResult: a queued command key and the JSON value returned by the local handler. The example's result_id helper reads an ID string from that JSON object.

{{example:commands:run-create}}

The title stored in the row is Buy milk, without the surrounding spaces. The task has a temporary local: ID. created.key identifies the queued command; task_id identifies the task row. They are different identifiers.

Pass that task ID to complete_task. You can do this immediately, while still offline. Its handler updates the task and inserts an activity entry in the same command.

{{example:commands:run-complete}}

The task is now done and the activity exists. There are two queued commands total: one creation and one completion. Completion contains two local writes, but contributes just one queue record.

What calls what in Rust?

The functions in this example are application code, not extra library APIs. CommandDefinition describes a name and argument types; it does not register a Rust handler. Your application calls its own handler after begin admits the request, then passes the handler's result to finish.

  1. Definition: which action is this, and which argument types are valid?
  2. Invocation: which values did the user supply this time?
  3. Handler: what business rules and local writes should run?
  4. Receipt: which queue key and local result does the caller receive?

The local result is not the server's later response. The Rust function body is not sent to the backend; the server receives the command name and invocation data.

1. Describe the create command

title is required because optional is false. This declares its type; it does not supply a title value or execute any business logic.

2. Pass a title and call the handler

Here is the application function used above. Its Rust parameter title becomes the title property of the invocation's JSON object. The matching definition and values are passed to begin. Once admitted, the application explicitly calls create_task_handler.

The example's json_object helper constructs a one-field JSON object. For this call, its field name is title and its value is the Rust string supplied by the caller.

{{example:commands:json-object}}

The entry point passes that object as the invocation arguments and explicitly calls the handler.

{{example:commands:create-task}}

This small entry point cancels an unadmitted request and returns Busy, so a caller can try the intent again with a new request. A host that retains queued requests can instead retry that same pending request until it is admitted. Never run the handler when begin returns false.

NOW_MS is the fixed 1000 ms fixture clock, and ada is its example identity. An application captures its actual context once per action; the server must authenticate the user independently.

3. Put your business logic in a named function

create_task_handler reads the arguments actually admitted for this request through scope_args. The example's string_argument helper extracts the named string. The handler trims it and rejects a blank title with the application-defined TodoError::BlankTitle.

{{example:commands:create-handler}}

The create_task_handler(db, request) call in the entry point is the application's choice of business function. Replace that call with your own handler, or call shared business services from inside it; the command name alone does not dispatch Rust code.

This is where you add application rules, derived fields or further scoped reads and writes. The returned JSON object contains the new task ID. It is the value that the caller later reads through created.result; it is not automatically the inserted row.

4. Finish on success, abort on failure

finish_or_abort is another small application helper. A successful handler result is passed to finish, which commits the local scope and returns the receipt. On a handler error, abort the scope and return that error without finishing.

{{example:commands:finish-or-abort}}

If finish itself fails, nothing is committed and the active request is consumed; retry the intent with a new request rather than aborting that consumed request.

CommandResult.key identifies durable queue work. CommandResult.result is the JSON value chosen by the local handler. To read the current task row, query the tasks table; the complete program checks its title and done flag after each step.

5. Describe completion and its reference argument

Completion takes a task ID, not another title. It is a string argument, and reference_paths tells the core that this string refers to a row. That declaration is needed for dependency tracking and ID rewriting when the task was created offline.

{{example:commands:complete-definition}}

6. Perform several writes in one handler

complete_task_handler reads task_id, uses the application helper fetch_task to read the task through the active scope, updates it, then inserts an activity. Both writes use the same request. The application-defined TodoError::UnknownTask handles a missing row.

{{example:commands:complete-handler}}

The function returns both IDs. It does not call finish between writes: the same finish_or_abort helper commits everything once the handler succeeds.

The completion entry point follows the same sequence as creation, with a different definition, argument and handler.

{{example:commands:complete-task}}

What if a later insert fails?

The executable tests deliberately cause the activity insert to fail after the task update was staged. The handler returns an error, finish_or_abort calls abort, and the prior task, activities and queue state remain unchanged. The tests then retry the same intent successfully with a new request. This is a failure demonstration, not an invalid-write pattern to copy.

The same rule applies to several inserts or updates in a loop, or to scope_apply_batch: keep one request for all operations and finish only after every step succeeds. Do not begin a nested command inside the handler. Starting separate commands does not combine them into one atomic command.

How these two commands sync and get server IDs

This section resumes the caller sequence after creating and completing the task. No network client is installed by the core. Your transport sends its prepared envelopes to your authenticated backend, whose own handlers process and deduplicate these named actions.

The first batch sends creation only. Completion waits because its task_id refers to the locally created task. The program also checks that a due retry has the same frozen envelope.

{{example:commands:first-push}}

The example's confirm helper stands in for recording a successful server response and reconciling one created ID. It takes the command key, the local row ID, the server's JSON result and the name of the result field containing the authoritative ID. That field name is this app's explicit server-response convention, not a core inference rule. An actual transport decodes its response through the wire codec.

{{example:commands:confirm}}

The server has assigned server-task-1. Map the creation's task ID when confirming that command.

{{example:commands:confirm-create}}

The next batch can now send completion, with task_id rewritten to server-task-1. The activity's task reference has been rewritten too; both facts are checked in the executable program.

{{example:commands:second-push}}

Completion also created a row: its activity needs its own mapping. Every command-created ID must be covered by that command's reconciliation plan. This is separate from the handler's local result.

{{example:commands:confirm-complete}}

After both confirmations, there is no live work in the queue. See durable retries and reconciliation for protocol and recovery details.

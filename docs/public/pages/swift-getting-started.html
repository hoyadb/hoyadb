Run a Todo app in Swift

This follows the same flow as JavaScript: open a database, read and watch tasks, add one with a command, then sync it. Every snippet comes from one Swift program that the documentation build compiles and runs.

The Swift binding is a local package in bindings/swift; it is not published. Add it to your app with a path dependency on the products HoyaDB and, for tests, HoyaDBTesting. The package links the native core from Artifacts/HoyaNative.xcframework, which is built from source and must match the source you use: rebuild it with python3 bindings/swift/build-artifacts.py (macOS and iOS slices) after changing the core. The documentation build does not touch that package. python3 docs/public/run_native.py build builds the core into target/documentation-languages with a macOS-only XCFramework in a copy of the package, and python3 docs/public/run_native.py swift runs this program against it.

Differences from JavaScript: Database is an actor, so every call is async. Values are typed: row fields are Cell values such as .string("Buy milk"), and command arguments and results are JSONValue. There is no query builder: a Query is a value with predicates and an order. Sync is explicit, step by step.

1. Describe your data

A schema lists your tables and the type of each column. Here a task has a title and a done flag. The same three imports serve the rest of the program: HoyaDB is the binding and HoyaDBTesting provides the stand-in server used in step 7.

{{example:swift:schema}}

A column is required unless you pass optional: true. Other kinds are .integer, .float, .timestamp and .reference.

2. Open one database

Create the database actor and open it with the schema. This example uses memory storage, which is ideal for trying things out.

{{example:swift:open}}

Open once when your app starts and share the actor. Memory storage is lost on close. For data that persists, openProtected takes a directory, a file name and a 32-byte key that your app owns; see persistence and key ownership.

3. Query

A Query names a table, its predicates and an order. Keep it in a constant: the next step watches the same query. Fetching runs locally, so it works offline.

{{example:swift:query}}

A new database has no tasks yet, so this first fetch is empty. Predicate operators are .equal, .notEqual, .less, .lessOrEqual, .greater, .greaterOrEqual and .oneOf. Several predicates must all match.

4. Watch the results

observe calls your closure with the query's current rows, then again after each change. Here it hands the rows to Seen, a small thread-safe recorder defined in the full program that lets the example check what the callback received; in an app, update your UI state instead.

{{example:swift:observe}}

The callback receives a Result: rows on success, or the delivery error. It runs on the executor you pass, by default the main queue, so it can update your UI directly. Keep the returned Subscription and cancel it when the view goes away.

5. Define a command and its local handler

A command has a definition, a stable name with a version suffix and the arguments it takes, and a local handler that runs on the device. Your server recognizes the command by its name. The handler reads its arguments from its scope and inserts the new task through it. CheckFailure is the example's own error type; throw whatever error suits your app.

{{example:swift:command-definition}}

Use the scope, not the database, for reads and writes inside a handler: they commit together when the handler returns, and nothing is kept if it throws.

6. Run it

command runs the handler from step 5 with the arguments and a captured context, and returns the key of the queued command with the handler's result.

{{example:swift:execute}}

The new task already appears in the watched query from step 4, under a temporary local: ID, and the command waits in the queue to sync. The example fixes the time at 1000 ms so that it is repeatable; pass the current time in an app. The context is recorded with the command. It is information for your server, not proof of who the user is.

7. Your server

Your server has its own handler for add-task-v1, and it decides the final outcome. Here FakeTransport from HoyaDBTesting plays the server and answers with the task's real ID.

{{example:swift:backend}}

In an app, replace it with your own HTTP client that sends the envelopes from the next step to your API.

8. Sync and confirm

preparePush returns the waiting commands as JSON envelopes; send them to your server and pass its answer to receiveWire. Each answer the server confirmed then waits in pendingReconciliations() until you reconcile it. A command that created rows must map every local: ID it created to the ID your server assigned.

{{example:swift:sync}}

After reconciling, the command is applied and the task has the ID server-task-1: HoyaDB renames the row everywhere, including in watched queries. See reconciliation.

9. Close

Cancel the subscription when the view no longer needs it, and close the database when your app shuts down.

{{example:swift:close}}

Continue with the Swift reference and sync. The verification result records the build and the run.

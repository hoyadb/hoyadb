Plan the authoritative change

A received outcome does not itself rewrite local rows. Supply a ReconcilePlan with writes and local-to-server ID mappings. A mapping renames identities and typed references through the existing rules. Every locally created command ID needs its server mapping. An empty plan can confirm an action without created identities when no replacement is needed. The executed command example supplies the required identity mapping.

Guard writes outside the optimistic set

Use reconcile_guarded for an authoritative correction that writes outside the command's optimistic closure. Each CorrectionGuard supplies the complete expected public fields or None for absence. A stale expectation or commit-time guard race refuses with RollbackConflict rather than applying a partial plan.

Core checks the closure proof before an inverse rewrite. Current entity overlap fallback can rebase supported correction/rollback cases while preserving later edits; this is not a general permission to overwrite arbitrary conflicts. A refusal leaves the attempted operation unapplied and recovery work retained.

Choose the existing recovery operation deliberately

OperationPurpose
reconcile / reconcile_guardedApply or confirm a retained authoritative result
rollbackUndo eligible optimistic recovery work if the proof still permits it
cancelWithdraw queued, sent or rejected work; late replies are ignored. If its inverse conflicts, returns RollbackConflict while recording Cancelled and retaining recovery data
forgetRemove eligible non-live history; live dependencies still protect producers
request_redeliveryRequest a lost result again, using the existing frozen identity
Stop/Discard policy is approved design, not implemented public API in this source. There is no documented discard method to call yet. Do not turn a RollbackConflict into success or modify internal records by hand.

Source: reconciliation and entity overlap fallback.

JavaScript creation mappings

The application callback receives {key, kind, created, outcome}. The created ID-to-table map comes from retained core records, so recovery works after reopen before command definitions are rebound. For a known one-row creation command, the tutorial maps that ID to its backend result. Multi-row commands must map every created ID explicitly. The binding fills missing identity mappings for entity-created final IDs, preserving every mapping supplied by the application. Core validation remains authoritative.

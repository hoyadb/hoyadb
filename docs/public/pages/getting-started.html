What you will build

A small Todo app that works offline. Tasks come from your server, you read and watch them locally, you complete one with a command, and the change syncs back to the server. Every snippet below is a piece of one complete file that the documentation build runs in Node and in a browser. You can read the whole file afterwards.

The packages are local and unpublished. Build them as described in installation, then import @hoyadb/client. The same import works in Node and in the browser, and loads the database engine for you.

1. Describe your data

A schema lists your tables and the type of each column. Here a task has a title, a done flag, and two optional fields filled in when it is completed.

{{example:application:schema}}

2. Connect your server

HoyaDB never makes network requests itself. You give it a transport: an object whose push sends local changes to your server and whose pull fetches server changes. This tutorial uses the test backend from @hoyadb/testing, which plays the server in the same process. It already has two tasks, and it knows how to answer the complete-task-v1 and add-task-v1 commands defined below.

{{example:application:backend}}

3. Open the database

Open one database when your app starts and share it. engine: 'memory' keeps data in memory, which is ideal for trying things out. context describes who is using the app, and is attached to every command. entities lists tables that sync field by field with the server. reconcile confirms each command the server accepted; step 9 explains it. The first sync() pulls the server's tasks.

The server must authenticate the user itself; context is supplied by the app and is not proof of identity.

{{example:application:open}}

4. Read data

Queries run locally, so they work offline. Rows come back as plain objects: task.title, task.done.

{{example:application:query}}

5. Watch data

observe calls your function with the current rows, then again whenever they change. Use it to keep your UI up to date. It returns a function that stops watching.

{{example:application:observe}}

6. Define a command

A command is a named, versioned action such as "complete a task". You write its handler once for the app. It runs immediately on the device, so the user sees the result at once, and your server runs its own version of the same command later and has the final say.

The handler receives three things:

  • db: a view of the database for this command only. Its writes become visible to everyone else together when the handler returns.
  • args: the arguments you pass to execute.
  • ctx: who is acting (ctx.identity) and when (ctx.now()).
{{example:application:command-definition}}

7. Run it

Bind the definition to your database once, then call execute. You get back what the handler returned. If the handler throws, nothing is saved.

{{example:application:execute}}

8. Sync with the server

sync() sends the queued command to the server and records the server's answer. Use db.startSync() instead to keep syncing in the background with automatic retries.

{{example:application:sync}}

9. Create a task

A command can also create rows. The new task appears at once with a temporary local: ID, so your UI can show it offline.

{{example:application:create-command}}

When the server accepts the command, it assigns the task's real ID and returns it in its result. Your reconcile callback, from step 3, receives the local IDs the command created in created. It maps them to the server's IDs, and HoyaDB then renames the row everywhere.

{{example:application:create-execute}}

10. Clean up

Stop watchers you no longer need. Calling the function that observe returned stops that watcher.

{{example:application:cleanup}}

Close the database when your app shuts down. The full file closes it in a finally block, so it is also closed if a step fails.

{{example:application:close}}
